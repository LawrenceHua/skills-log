# Append-only work ledger

A run that reports its work from memory produces a report. A run that appends one schema-valid row per action, finding, change and verification produces a **record**: someone else can read it, parse it and re-run the checks in it.

The ledger answers "what did we do." A second file, the backlog of re-runnable checks, answers "is it still true." They need different files.

## 1. The label set is closed

Use exactly four verdict labels, nothing else:

`VERIFIED` · `CODE-SHIPPED-NOT-VERIFIED` · `BLOCKED` · `INCONCLUSIVE`

A row labelled `DONE`, `FIXED`, `REPORT` or `CORRECTION` is unreadable to any tool that parses the four and has the same standing as no row. In one measured ledger about one row in ten used a non-verdict as the label because the event field already said "correction" and the label field was duplicating it.

## 2. The row

One JSON object per line (JSONL):

```json
{"at":"2026-01-15T19:55:00Z","lane":"migration-q1","event":"verification","what":"...","label":"VERIFIED"}
```

- `at`: UTC timestamp generated by the system clock, never typed by hand.
- `event`: one of `finding`, `change`, `verification`, `decision`, `correction`, `cross-check`, `close`, `dispatch`, `deadline`, `retraction`.
- `label`: one of the four labels.
- `what`: one line, never a raw newline. Collapse whitespace on write, so one row is always one line (a title containing a newline once made 37 rows render as 48 lines and invented a divergence that did not exist).

## 3. What to record, and when

Record at the moment it becomes true, not at the end of the run.

| Event | Record it when |
|---|---|
| `finding` | you learn something from a live probe or a file |
| `change` | you write or ship anything; name the backup and the proof command |
| `verification` | an external reference confirms or refutes a claim |
| `decision` | you pick a default instead of asking; name the rollback |
| `correction` | you withdraw your own claim; a retraction is a claim and needs the same evidence |
| `close` / `dispatch` / `deadline` | a milestone, an agent sent out, a time-boxed anchor |

A `what` of "fixed it" is not a row. It must name the **reference it was compared against**: the command, the `file:line`, the third party. If the builder chose the reference, say so; that row is a report, not a verification.

## 4. Build a small enforcing tool, not a convention

A short script (standard library only) with three commands is enough:

```
ledger append --lane L --event change --label VERIFIED --what "..."
ledger check  --lane L        # exit 1 on any contract violation
ledger tail   --lane L -n 5
ledger --selftest             # proves each guarantee by trying to break it
```

Requirements:

- **Atomic and locked** appends, so concurrent writers never interleave.
- **A missing lane directory is a refusal**, not a new file, so a typo cannot silently start a second ledger.
- **Bad label or bad event is refused** at append time.
- **Repair is loud.** If the last byte of the file is not a newline, an append must first write the missing newline *inside the lock*, warn on stderr, and use a distinct exit status (for example 3, meaning "append succeeded, ledger needed repair") plus a line in a sidecar `.repairs` file. A silent repair erases its own evidence.
- **Readers decode leniently.** Split rows as bytes and decode each with replacement so one bad byte is reported by line number and the rest of the file is still checked.
- **Share one reader** between `check` and `tail`. A fix applied to one reader is a fix applied to none until you grep for the other readers.

## 5. Negative controls are part of the row

Any check you append must be one that can fail. Prove each tool guarantee by breaking it in the selftest: bad label refused, bad event refused, a corrupt row makes `check` fail, an unterminated last line cannot swallow the row before it, a non-UTF-8 byte is reported by line. State concurrency claims precisely: a stress test of 8 overlapping writers plus sequential appends proves 8-way overlap, not 40.

## 6. Legacy rows: report them, never rewrite them

A ledger that predates the tool will fail `check` on its old rows. That is a true report, not a bug. Do not edit history to turn the check green; the wrong labels are evidence of the drift the tool exists to stop. Record the count once, then keep appending contract-clean rows.

## 7. Pair it with a backlog of re-runnable checks

- `LEDGER.jsonl`: append-only, one row per event. "What did we do."
- `BACKLOG.md`: one `### ITEM` per open criterion with `title / label / class / done / check`. "Is it still true, and how would a stranger know."

A small runner executes every item's `check:` and prints a table:

```
ID              LABEL       CHECK   CLASS   DONE-CRITERION
LOG-SELFTEST    VERIFIED    MET     BUILD   selftest prints all checks passed
PR-QUEUE        BLOCKED     OPEN    OWNER   0 open PRs on the product repo
```

**The rule that justifies the second file:** a `VERIFIED` item whose own check does not pass is a **CONTRADICTION**; the runner prints it and exits 1. That inverts the usual failure, where a stale label is invisible because nothing ever re-reads it. The converse is also caught: a non-`VERIFIED` item whose check now passes prints `READY TO PROMOTE`, so work that quietly got fixed is re-labelled instead of sitting blocked forever.

Lessons from building it:

- **A check built on a guessed literal measures the literal.** Run each check once before writing it down, and prove the arms of a composite check one at a time.
- **A timeout is not a measured OPEN.** Render `timed out` in the table; "we never asked" and "we asked and it failed" are different.
- **The runner needs its own selftest** with a fixture item per outcome: met, open, contradiction, promote, schema error, missing file.
- **Set the executable bit after any programmatic write**, then run the tool once for real; do not assume.

## When to use

- Starting or continuing a multi-step run whose work another agent or person will read.
- Before a compaction or handoff, so state lives in a file rather than in context.
- A report needs a receipt a stranger can re-check; or a "VERIFIED" claim may have gone stale.

## How to use

1. Copy this folder to `~/.claude/skills/append-only-work-ledger/` (personal) or `.claude/skills/append-only-work-ledger/` inside a project.
2. Ask Claude Code to use the `append-only-work-ledger` skill by name.

Example prompts:

- "Use the append-only-work-ledger skill: write the small standard-library ledger script with append, check, tail and a selftest that tries to break each guarantee, then start a ledger for this migration."
- "Use append-only-work-ledger to turn our open acceptance criteria into a BACKLOG.md with a re-runnable check per item and a runner that flags any VERIFIED item whose check fails."
